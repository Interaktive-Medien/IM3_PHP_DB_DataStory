Was ist eine Datenbank?

Warum nicht einfach eine Datei?

Eine JSON-Datei zu speichern wäre möglich.

  • Für 258 Zeilen funktioniert das sogar gut
  • Ihr könnt sie öffnen und lesen
  • Sie liegt einfach im Ordner

Das ist mühsam:

  • Eine einzelne Stadt heraussuchen müsst ihr selbst programmieren
  • Eine Zeile ergänzen heisst: die ganze Datei neu schreiben
  • Zwei Abrufe gleichzeitig können die Datei zerstören
  • Sortieren und Zählen macht niemand für euch

Eine Datenbank ist ein Programm, das genau diese Arbeit übernimmt.

Sie beantwortet Fragen an die Daten, statt nur Text aufzubewahren.

Die Frage kommt fast immer, und sie ist berechtigt – für ein kleines historisches Dataset wäre eine Datei tatsächlich vertretbar. Das ehrliche Argument ist deshalb nicht «Dateien sind schlecht», sondern: Sobald gesucht, gefiltert und dazugeschrieben wird, programmiert ihr sonst eine halbe Datenbank nach. Für Gruppen mit Live-Sammlung ist der dritte Punkt der entscheidende.

Eine Tabelle ist eine Liste mit festen Spalten

Tabelle heat_summers
idcityyearmeasurement_dayshot_daysmax_temperature_c
1Bern2022921434.6
2Bern2023921236.3
3Chur2023921435.4
  • Eine Zeile ist ein Datensatz
  • Eine Spalte ist ein Feld dieses Datensatzes
  • Alle Zeilen haben dieselben Spalten
  • Eine Datenbank enthält mehrere Tabellen
  • Jede Spalte hat einen festen Datentyp
  • Diese Struktur heisst Schema
Das ist dieselbe Struktur wie das Resultat aus dem Transform, nur an einem anderen Ort. Wer die Excel-Analogie braucht, darf sie hier haben – mit dem Unterschied, dass die Datenbank die Spaltentypen erzwingt und Excel nicht.

Relational

Daten stehen in Tabellen und sind untereinander verknüpft.

  • Die Spalten stehen vorher fest
  • Abgefragt wird mit SQL
  • MySQL, MariaDB, PostgreSQL, SQLite

Passt, wenn alle Datensätze gleich gebaut sind.

Nicht relational

Daten stehen als einzelne Dokumente nebeneinander.

  • Jedes Dokument darf andere Felder haben
  • Jedes System hat seine eigene Abfragesprache
  • MongoDB, Firebase, Redis

Passt, wenn die Struktur offen bleiben muss.

Bewusst kurz gehalten, es ist eine Einordnung und kein Vergleichstest. Der Anschluss an den letzten Block ist das Argument: Nach dem Transform sind alle Zeilen gleich gebaut – das ist die Voraussetzung, unter der eine Tabelle das einfachere Werkzeug ist. «NoSQL» als Begriff nennen, falls er aus der Klasse kommt.

  • Eine Datenbank gab es noch nicht

Das Datenmodell

Von der Zeile im Resultat zur Tabelle in der Datenbank

Eine Zeile bleibt eine Zeile

Resultat aus dem Transform 

{
  "city": "Bern",
  "year": 2023,
  "measurement_days": 92,
  "hot_days": 12,
  "max_temperature_c": 36.3
}
→
Zeile in der Datenbank
SpalteWert
cityBern
year2023
measurement_days92
hot_days12
max_temperature_c36.3

Die Untersuchungseinheit aus dem Transform wird zur Zeile in der Tabelle.

Bei uns ist das eine Stadt in einem Sommer.

Der Datenvertrag ist damit bereits fast das Datenmodell – das ist die gute Nachricht dieses Kapitels. Wer im Transform sauber entschieden hat, was eine Zeile bedeutet, hat die Tabelle schon entworfen. Feld für Feld dasselbe, nur an einem anderen Ort. Dass der Stadtname später noch in eine eigene Tabelle wandert, kommt in fünf Folien.

Jede Spalte bekommt einen Datentyp

Typ Wofür Bei uns
INTganze Zahlenid
SMALLINTkleine ganze Zahlenyear, hot_days
DECIMAL(4,1)Kommazahl mit fester Genauigkeitmax_temperature_c
VARCHAR(80)Text bis zu einer Höchstlängecity
DATE, DATETIMEDatum und Zeitpunktin vielen Projekten
BOOLEANja oder neinin vielen Projekten

Der Typ ist eine Zusage: Was nicht hineinpasst, bleibt draussen.

Der Unterschied zur Datei auf den Punkt gebracht: In einer JSON-Datei kann in hot_days plötzlich «viele» stehen, in der Spalte nicht. Praktischer Hinweis fürs Projekt: Für Text unbekannter Länge gibt es TEXT, für Zeitpunkte immer DATETIME statt Text nehmen – sonst sortiert später nichts richtig. Genauere Typen stehen im Cheatsheet.

Der Primärschlüssel

Jede Zeile braucht eine eindeutige Nummer, an der man genau sie erkennt.


id INT AUTO_INCREMENT PRIMARY KEY
  • PRIMARY KEY heisst: Dieser Wert kommt kein zweites Mal vor
  • AUTO_INCREMENT heisst: Die Datenbank vergibt die Nummer selbst
  • Ihr schreibt diese Spalte beim Einfügen deshalb nie mit

Ohne Primärschlüssel könnt ihr eine einzelne Zeile später nicht sicher ansprechen.

Die drei Regeln zuerst, das Beispiel dazu steht auf der nächsten Folie. AUTO_INCREMENT heisst wörtlich «automatisch hochzählen» – die erste Zeile bekommt 1, die nächste 2. Gelöschte Nummern werden nicht wiederverwendet.

Die id in unseren Zeilen

drei Zeilen aus heat_summers
idcityyearhot_days
1Bern202214
2Bern202312
3Chur202314
  • Das Jahr 2023 steht zweimal da, die id nie
  • Stadt und Jahr zusammen wären auch eindeutig, aber umständlich
  • Mit WHERE id = 2 erwischt ihr genau eine Zeile

Die Nummer bedeutet nichts, sie zeigt nur auf genau diese Zeile.

Frage in die Klasse, bevor die Liste kommt: Könnten wir nicht das Jahr als Schlüssel nehmen? Antwort: nur solange eine Stadt drin ist – bei drei Städten kommt 2023 dreimal vor. Die Kombination aus Stadt und Jahr wäre tatsächlich eindeutig, und genau die brauchen wir am Ende noch einmal als UNIQUE-Regel. Als Schlüssel bleibt die eigene, bedeutungslose id die verlässlichste Wahl.

alles in einer Tabelle

………

Drei Städte, 86 Jahre, 258 Zeilen.

  • Jeder Stadtname steht 86-mal in der Tabelle
  • Ein Tippfehler erzeugt eine vierte Stadt, die es nicht gibt
  • Eine Umbenennung müsstet ihr 86-mal machen

Wiederholte Werte sind hier kein Platzproblem, sondern ein Fehlerrisiko.

Bei sehr grossen Datenmengen werden sie irgendwann auch ein Platzproblem.

«Zürich» und «Zuerich» nebeneinander ist der Klassiker – im Chart erscheinen dann zwei Städte. In unserer Grössenordnung ist Speicherplatz das schwächste Argument: 258-mal ein Wort ist nichts. Bei Millionen Zeilen kippt das, und dann zählt beides. Für eure Projekte gilt trotzdem der erste Satz: Es geht um die eine Stelle, an der ein Wert steht und geändert werden kann.

Darum: Zwei Tabellen und ein Fremdschlüssel

cities

heat_summers

  • Der Stadtname steht jetzt genau einmal in cities
  • city_id verweist auf die id in cities und heisst deshalb Fremdschlüssel
  • Gelesen wird die Linie als: eine Stadt hat viele Sommer
  • Jeder Sommer gehört aber nur zu einer Stadt
Diese Zeichnung ist das ERM, das die Klasse gleich selbst für ihre Daten macht. Die Fremdschlüsselspalte trägt den Namen der Zieltabelle im Singular plus _id – das ist Konvention und macht sie sofort erkennbar. Wichtig für den Code-Along: Die Datenbank lehnt eine city_id ab, zu der es keine Stadt gibt, und schützt euch damit vor verwaisten Zeilen.

So plant ihr euer eigenes Modell

Vier Fragen, und zwar auf Papier und vor dem ersten SQL-Befehl.

  • Was bedeutet eine Zeile in euren Daten?
  • Welche Felder hat sie, und welchen Datentyp hat jedes davon?
  • Welcher Wert wiederholt sich in fast jeder Zeile?
  • Woran erkennt ihr eine einzelne Zeile eindeutig?

Der wiederholte Wert ist der Kandidat für die zweite Tabelle.

Mehr als zwei Tabellen braucht in diesem Kurs kein Projekt – ausser ihr kombiniert mehrere Datensätze.

Genau diese vier Fragen stehen auf dem Arbeitsblatt der Papierübung. Die Antworten auf Frage eins und zwei stehen bereits im Datenvertrag aus dem Transform – das laut sagen, es spart den Gruppen die halbe Übung. Zeitrahmen 35 Minuten, danach hängt jede Gruppe ihr Modell auf.

Wann eine Tabelle genügt

Eine Tabelle

  • Kein Wert wiederholt sich auffällig
  • Alle Felder beschreiben dieselbe Sache
  • Beispiel: Messwerte einer einzigen Station

Zwei Tabellen

  • Ein Name oder eine Kategorie wiederholt sich ständig
  • Diese Sache hat eigene Felder wie Koordinaten oder Farbe
  • Beispiel: Städte und ihre Messungen

Eine schlecht geschnittene zweite Tabelle kostet mehr, als sie einbringt.

Im Zweifel klein anfangen und die Aufteilung begründen können.

Die Gruppen fragen erfahrungsgemäss genau hier nach ihrem eigenen Fall. Als Faustregel taugt: Wenn ihr die zweite Tabelle nur anlegt, weil es «richtiger» aussieht, lasst es. Wenn ihr sie anlegt, weil ihr sonst einen Namen hundertmal schreibt, macht es.

SQL

Die Sprache, in der man mit einer Datenbank redet

Vier Befehle reichen für alles

Befehl Was er tut Wo wir ihn brauchen
INSERTschreibt eine Zeile hineinheute, in load.php
SELECTholt Zeilen herausheute zum Kontrollieren, später in unload.php
UPDATEändert vorhandene Zeilenselten
DELETElöscht Zeilenzum Aufräumen

SQL ist eine eigene Sprache und hat mit PHP nichts zu tun.

Wir schicken sie als Text an die Datenbank und bekommen ein Resultat zurück.

Kurz einordnen, dass SQL älter ist als fast alles andere im Kurs und sich seit Jahrzehnten kaum verändert hat – gelernt wird das hier also nicht für dieses Semester. Grossschreibung der Befehle ist Konvention und keine Vorschrift, sie macht die Abfrage lesbar. Das Semikolon am Ende gehört dazu.

Die Tabellen anlegen


CREATE TABLE cities (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE heat_summers (
  id                INT AUTO_INCREMENT PRIMARY KEY,
  city_id           INT NOT NULL,
  year              SMALLINT NOT NULL,
  measurement_days  SMALLINT NOT NULL,
  hot_days          SMALLINT NOT NULL,
  max_temperature_c DECIMAL(4,1),
  FOREIGN KEY (city_id) REFERENCES cities(id)
);
  • NOT NULL verlangt einen Wert, UNIQUE verbietet Wiederholungen
  • max_temperature_c darf leer bleiben und ist dann NULL
  • Dasselbe könnt ihr in phpMyAdmin auch zusammenklicken
Das ist die Zeichnung von vorhin als Text – Feld für Feld dieselbe Reihenfolge. Die Tabelle cities muss zuerst existieren, sonst zeigt der Fremdschlüssel ins Leere. Wichtig für den Anschluss an den Transform: NULL ist hier erlaubt, weil es «nicht gemessen» heisst, und genau das hatten wir letzten Block als Regel. Im Unterricht klicken wir es im GUI zusammen und lassen uns von phpMyAdmin das SQL dazu anzeigen – dann sehen sie beide Wege nebeneinander.

INSERT schreibt eine Zeile


INSERT INTO cities (name)
VALUES ('Bern');

INSERT INTO heat_summers (city_id, year, measurement_days, hot_days, max_temperature_c)
VALUES (1, 2023, 92, 12, 36.3);
  • Zuerst die Spalten, dann in derselben Reihenfolge die Werte
  • Text steht in einfachen Anführungszeichen, Zahlen stehen ohne
  • Die Spalte id fehlt, weil die Datenbank sie selbst vergibt

258-mal dieser Befehl mit anderen Werten – das ist der ganze Ladevorgang.

Hier lohnt sich der Vorgriff: Genau diesen Befehl schreiben wir gleich einmal hin und lassen ihn von PHP 258-mal mit anderen Werten ausführen. Die 1 in der zweiten Anweisung ist die id, die Bern beim ersten INSERT bekommen hat – dass die von Hand hingeschrieben ist, ist das Problem, das später lastInsertId löst.

SELECT zum Nachschauen


SELECT * FROM heat_summers;

SELECT year, hot_days
FROM heat_summers
WHERE city_id = 1
ORDER BY year;
  • Der Stern holt alle Spalten
  • WHERE wählt Zeilen aus
  • ORDER BY sortiert das Resultat

Aus diesem Befehl wird später der JSON-Endpunkt für das Frontend.

Heute braucht ihr das nur, um zu prüfen, ob das Laden geklappt hat.

Bewusst knapp – SELECT ist das Thema des nächsten Blocks, hier ist es reines Kontrollwerkzeug nach dem Laden. Praktisch im Unterricht: nach dem Code-Along in phpMyAdmin SELECT COUNT(*) laufen lassen, das Resultat muss 258 sein.

UPDATE und DELETE


UPDATE heat_summers SET hot_days = 13 WHERE id = 42;

DELETE FROM heat_summers WHERE id = 42;

DELETE FROM heat_summers;
  • Beide wirken auf alle Zeilen, auf die die Bedingung zutrifft
  • Ohne WHERE trifft sie auf jede Zeile zu
  • Die dritte Zeile leert also die ganze Tabelle

Es gibt keine Rückfrage und kein Rückgängig.

Der Moment für die Warnung, aber ohne Drama: In unserem Ladeskript ist das letzte Kommando gleich Absicht. Merksatz: erst als SELECT mit derselben WHERE-Bedingung ausprobieren, dann das SELECT durch UPDATE oder DELETE ersetzen. Wer produktiv arbeitet, macht vorher einen Export in phpMyAdmin.

phpMyAdmin

phpMyAdmin ist eine Oberfläche im Browser für eure Datenbank.

Was ihr klickt, könnt ihr also auch lesen und lernen.

Gefüllt wird sie danach nur noch von load.php.

PDO

Wie PHP mit der Datenbank spricht

PHP spricht kein SQL

load.phpunser PHP-Skript
→
PDOschickt SQL hin und Resultate zurück
→
MariaDBführt SQL aus
  • PDO ist fest in PHP eingebaut und heisst PHP Data Objects
  • Wir übergeben SQL als Text und bekommen PHP-Arrays zurück
  • Für MySQL, MariaDB, PostgreSQL und SQLite funktioniert es gleich

PDO ist ein Helfer wie fetchJson() beim Extract, nur für Datenbanken statt APIs.

Der Vergleich mit fetchJson trägt weiter, als er zuerst scheint: Auch dort ging eine Anfrage raus und ein Array kam zurück, und auch dort war das Protokoll dazwischen nicht unser Thema. Wer mysqli aus dem Internet kennt: dasselbe Ziel, ältere Schnittstelle, wir nehmen PDO.

Die Verbindung aufbauen

config.php – einmal im Hauptordner 

<?php
$host     = 'konto.mysql.db.hostpoint.ch';
$dbname   = 'konto_im3';
$username = 'konto_im3';
$password = '…';
$dsn = "mysql:host=$host;dbname=$dbname;charset=utf8mb4";
load.php – irgendwo im Kursordner 

// drei Ordner nach oben zum Hauptordner
require __DIR__ . '/../../../config.php';

$pdo = new PDO($dsn, $username, $password, $options);
  • Es gibt genau eine config.php für alle Übungen
  • Der DSN sagt PDO, welche Datenbank wo liegt
  • Host, Datenbank und Benutzer beginnen bei Hostpoint mit dem Kontonamen

config.php enthält euer Passwort und darf nie auf GitHub landen.

Tragt die Datei in .gitignore ein, bevor ihr das erste Mal committet.

DSN heisst Data Source Name und ist einfach die Adresse der Datenbank. Der Grund für die eigene Datei: Alle Code-Alongs teilen dieselben Zugangsdaten, und das Passwort bleibt aus dem Repository draussen. Die $options mit ERRMODE_EXCEPTION stehen ebenfalls in config.php und kommen auf der übernächsten Folie. «konto» steht für den eigenen Kontonamen: Hostpoint setzt ihn vor Host, Datenbank und Benutzer, und wer ihn vergisst, bekommt «Access denied» oder «Unknown database». Das ist der häufigste Fehler im ganzen Block.

Zugangsdaten gehören nicht ins Repository

So arbeitet das Team damit.

  • config.php steht in .gitignore
  • Eine config.template.php ohne Werte liegt im Repository
  • Jede Person kopiert sie und trägt ihre eigenen Werte ein
.gitignore
config.php

Auch KI-Werkzeuge bekommen diese Datei nicht zu sehen.

Ein Passwort, das einmal in einem Commit steht, bleibt in der Historie stehen.

Wer es trotzdem hochgeladen hat, ändert sofort das Passwort.

Im Repository liegt bereits eine config.template.php, die genau dafür gedacht ist. Der letzte Satz ist der Grund, warum das jetzt kommt und nicht später: Nachträglich aus der Historie entfernen ist mühsam, und öffentliche Repositories werden automatisiert nach genau solchen Dateien durchsucht. Wer es doch einmal committet, ändert das Passwort und diskutiert nicht.

Erst vorbereiten, dann ausführen

Werte schreiben wir nie direkt in den SQL-Text.


$insertSummer = $pdo->prepare(
    'INSERT INTO heat_summers (city_id, year, measurement_days, hot_days, max_temperature_c)
     VALUES (:city_id, :year, :measurement_days, :hot_days, :max_temperature_c)'
);

$insertSummer->execute([
    'city_id' => 1,
    'year' => 2023,
    'measurement_days' => 92,
    'hot_days' => 12,
    'max_temperature_c' => 36.3,
]);
  • Die Namen mit Doppelpunkt sind Platzhalter und keine Werte
  • prepare schickt den Bauplan, execute schickt die Werte
  • Die Datenbank hält beides getrennt, deshalb kann kein Wert zu Code werden
Das Prinzip an der Tafel: Der Satzbau geht einmal hin, die Wörter kommen später und einzeln. Deshalb spielt es keine Rolle mehr, was in einem Wert steht. Die Schlüssel im Array müssen genau den Platzhaltern entsprechen, ohne Doppelpunkt – das ist die häufigste Fehlermeldung im Code-Along.

Einmal vorbereiten, 258-mal ausführen


foreach ($rows as $row) {
    $insertSummer->execute([
        'city_id'           => $cityIds[$row['city']],
        'year'              => $row['year'],
        'measurement_days'  => $row['measurement_days'],
        'hot_days'          => $row['hot_days'],
        'max_temperature_c' => $row['max_temperature_c'],
    ]);
}
  • prepare steht vor der Schleife und läuft genau einmal
  • execute steht in der Schleife und läuft für jede Zeile
  • Das ist schneller und lesbarer als 258 zusammengebaute Befehle

Die Werte kommen unverändert aus dem Transform.

Hier schliesst sich der Kreis zum letzten Block: Weil der Transform bereits echte Zahlen und den vereinbarten Datenvertrag liefert, ist diese Schleife so kurz. Wer hier noch umrechnen oder umbenennen muss, hat es im Transform vergessen – das ist eine gute Diagnose für die Projektgruppen.

Woher kommt die city_id?

Im Transform steht «Bern», in der Tabelle braucht es die Nummer von Bern.


$findCity->execute([$city]);
$id = $findCity->fetchColumn();

if ($id === false) {
    $insertCity->execute([$city]);
    $id = $pdo->lastInsertId();
}
  • fetchColumn holt den ersten Wert der ersten gefundenen Zeile
  • Ohne Treffer liefert es false, und dann legen wir die Stadt an
  • lastInsertId gibt die Nummer zurück, die die Datenbank gerade vergeben hat
Das Muster heisst «suchen, sonst anlegen» und begegnet euch in jedem Projekt mit zwei Tabellen wieder. Der Vergleich mit === false ist genau, weil die id 0 sonst wie «nicht gefunden» aussähe. Im Code-Along merken wir uns die gefundenen Nummern zusätzlich in einem Array, damit nicht 258-mal dieselbe Abfrage läuft.

Zwei Muster, je nach Datenquelle

Stand neu schreiben

Für einen historischen Datensatz, der jedes Mal vollständig kommt.


$pdo->exec('DELETE FROM heat_summers');

Diese Zeile steht vor der Schleife.

Dazuschreiben ohne Duplikate

Für eine Live-Sammlung, die über Wochen wächst.

  • Eine UNIQUE-Regel auf Zeitpunkt und Ort
  • Dazu INSERT IGNORE statt INSERT

Bei einer Live-Sammlung wäre Leeren fatal, weil die Vergangenheit nirgends sonst steht.

Die Entscheidung hängt allein daran, ob die Quelle die Vergangenheit noch einmal liefern kann. Open-Meteo liefert 1940 bis heute jederzeit neu, ein Sensor liefert nur jetzt. Gruppen mit Live-Sammlung müssen das heute festlegen; für sie steht das genaue INSERT-IGNORE-Beispiel im Cheatsheet. Wir bauen im Code-Along das linke Muster.

Wenn etwas schiefgeht


$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
];
  • Die erste Zeile sorgt dafür, dass Fehler laut abbrechen statt still zu scheitern
  • Die zweite lässt PDO Zeilen als assoziative Arrays zurückgeben

Lest die Fehlermeldung von unten nach oben und sucht den Tabellen- oder Spaltennamen darin.

Die drei häufigsten Fehler sind Tippfehler im Spaltennamen, falsche Zugangsdaten und ein Fremdschlüssel ohne passende Stadt.

ERRMODE_EXCEPTION ist die wichtigste Zeile des ganzen Setups: Ohne sie läuft ein fehlgeschlagenes INSERT einfach durch und die Tabelle bleibt leer. Typische Meldungen kurz vorlesen, damit sie im Code-Along wiedererkannt werden: «Unknown column», «Access denied», «Cannot add or update a child row». Alle drei sind eindeutig, wenn man sie einmal gesehen hat.
